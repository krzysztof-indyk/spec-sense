## SDDW interactive policy — `speckit.checklist` (scope + category approvals)

This policy changes **discovery, approval, and write timing only**. Preserve
the **standard Spec Kit checklist format and location**, core template,
feature context loading, quality dimensions, naming, item structure,
`CHK###` numbering, hook contract and append behavior. This command writes
**requirements-quality checklists**, not unit/integration tests or a verdict
on implemented code. `checklists/requirements.md` generated by core specify/
clarify is NOT a custom checklist to rewrite or mark as checked here.

### 1. Read-only discovery of scope

- Default to interactive, irrespective of an optional `--auto` flag: it may
  speed up research but NEVER bypass category approvals or final write consent.
- Inspect user input, relevant `spec.md` and (when present) `plan.md`,
  `tasks.md` and ratified constitution. Derive actual requirement-quality
  risks; **do not invent** a long catalogue of unrelated quality domains.
- Until all categories and final writing are explicitly approved, only
  inspect/read files and prepare proposals **in the chat**. Do not create
  `checklists/`, write or append `.md` files, run setup scripts that may
  write, mark existing items checked, modify spec/plan/tasks, or run
  write-capable extension hooks. Read-only prerequisite checks are allowed.
  Inspect hook declarations and disclose blockers; handle mandatory hooks
  at the authorized stage, never silently omit or misreport them.
- Ask **exactly one** adaptive scope question per reply, then STOP and wait.
  Prioritize purpose/audience, relevant domains, risk emphasis and exclusion
  boundaries only if they would change the checklist. Skip information
  already supplied. Avoid an arbitrary cap on questions but stop discovery
  as soon as scope is sufficiently clear.
- Summarize the agreed focus in a few lines and propose a short list of
  relevant **review categories** (e.g. API requirements, permissions,
  reliability) only if anchored in the feature. This is **not** permission
  to write them. If category boundaries are ambiguous, ask one question.

### 2. Approve each category before writing

1. Work through one category **at a time**. Propose its review purpose and
   the **actual candidate checklist questions**, not just a vague title.
   Each item must test the QUALITY of a written requirement: completeness,
   clarity, consistency, measurability, scenario coverage, edge cases, etc.
   Point to an exact spec section when available or mark a gap. Do not
   smuggle in new requirements as though already approved.
2. Keep a useful, concise list of exact proposed items so the user can
   inspect what will be generated. If many, preview in manageable chunks
   while maintaining a **single category-level approval** decision; never
   require sign-off on each item.
3. Ask one question: **approve, revise or reject this category?** STOP.
   If revised, show the changed wording and request approval again. If
   rejected, exclude it. Never advance to the next category without a
   decision. Don't redo approved categories unless a later choice materially
   changes their content; then show the delta for renewed approval.
4. Track categories, exclusions and user decisions **in session only**.
   Use no temporary files or unapproved checklist markdown. An existing
   domain checklist is not evidence that its items are reviewed or correct.

### 3. Confirm and generate only approved categories

- Summarize selected categories and item counts, excluded/deferred areas,
  output file path(s), and whether any existing checklist(s) will be
  **appended to**. Ask one final question: **"Generate or append only these
  approved requirements-quality checklist categories now?"** STOP.
  Category approval alone is not file write permission.
- If nothing is approved, do not create empty files or directories. If the
  user declines final approval, do not write or execute write-capable hooks.
- On final approval, re-check that source context hasn't materially changed,
  then run the **original standard checklist generation/validation and
  authorized hook workflow** using the **original template**. Only produce
  the approved categories and their approved questions. If a material new
  issue appears, discuss it before writing; do not silently expand scope.
- Existing custom `[domain].md` files are **append-only** (continue CHK
  numbering, do not delete/rewrite entries); new custom files begin CHK001.
  Remove duplicate proposed questions already present rather than appending
  a redundant item, and flag any material reductions for approval.
- All newly generated questions remain `[ ]` **unchecked**, with the
  appropriate requirement-quality markers. Never self-certify them with
  `[x]`; that belongs to the human reviewer, not implementation status.
- Report the generated file path(s), counts, and handoff to review or
  `speckit.clarify` if requirements gaps were identified. Do not auto-run
  implementation or another Spec Kit command.

### Communication

One focused question per turn; concise category reviews, full native
checklist formatting in files. No boilerplate or speculative questions.

## Decision Handoff — v0.6.0

- Use native active-feature resolution; never guess paths. Read relevant artifacts
  and pending sections before asking. Classify decisions in memory: approved,
  open, conflicting, later-stage or out-of-scope. Track source references.
- Reuse approved decisions, including semantically equivalent wording. Do not
  treat suggestions or defaults as approval. Reopen only missing details,
  material contradictions or new risks; explain what changed.
- Keep discovery read-only, including scripts/hooks. Preserve existing gates
  and `--auto` limits. Require no additional handoff approval for unchanged
  decisions; preview transfers in the existing final write summary.
- Apply forward-only adoption: read historical artifacts, but do not migrate
  old decisions. Add no registry, runtime, command or core template/script change.
  Never auto-invoke another stage. Reading a source grants no write permission.
- Re-read saved output; verify meaning, constraints and qualifiers. Account for
  every new approved decision. Report persisted, pending or unpersisted status;
  never claim complete persistence when missing or lose the only durable copy.

### Checklist boundary

- Reuse approved decisions; still check requirement quality and completeness.
  Preserve category/final approvals, unchecked CHK items and append-only writes.
- Never create pending entries in checklists, rewrite existing items or clean
  other artifacts. Report source entries as retained, not transferred.
- Label new product/design decisions unpersisted; checklist questions cannot
  replace canonical decisions. Recommend separate clarify/plan without invoking it.
